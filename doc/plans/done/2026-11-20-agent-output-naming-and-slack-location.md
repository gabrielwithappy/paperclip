# 에이전트 지침으로 적용하는 산출물 명명 규칙과 Slack 위치 안내 계획

## 목표와 범위

사용자가 요청한 작업 이름과 내용을 보고 프로젝트·작업 폴더와 산출물 파일을 식별할 수 있게 한다. 산출물 저장은 **에이전트 개인/로컬 공간이 아닌 프로젝트 워크스페이스 폴더 저장을 기본 원칙**으로 삼는다. 파일 산출물이 발생하는 작업에서는 **사용자에게 기본 프로젝트 폴더 경로로 저장할 것인지 먼저 확인(질문/안내)하고 동의를 받아 진행**한다. Slack 요청에는 같은 요청 스레드에서 작업명과 저장 예정 폴더를 확인·안내하고, 완료 시 확인된 위치와 산출물 링크를 전달한다.

**각 에이전트의 진입 지침과 보조 규칙 파일을 배포하는 방식으로 적용한다.** DB, API, UI, heartbeat, Runner, 어댑터, Slack 발행 코드와 업로드 helper는 변경하지 않는다. 앞선 계획의 `output_location` 필드, 서버 위치 결정, 실행 컨텍스트 확장, 원자적인 버전 예약 및 자동 Slack 안내 구현은 제외한다.

이번 요청은 계획 수정이다. 운영 에이전트 파일 변경·스킬 배포·Slack 발송은 아직 수행하지 않는다. 이후 적용 요청을 받으면 아래 순서로 진행한다.

대상은 기존·신규 에이전트 전체다. 보고서·설계서·이미지·영상·결과 묶음 등 사용자에게 전달할 생성 파일에 적용한다. 소스 코드·빌드 결과는 해당 저장소와 도구의 기존 경로 규칙을 따르고 PR·커밋 또는 실제 파일을 연결한다. 파일이 필요 없는 답변에 빈 폴더를 만들지 않는다.

## 1. 지침 관리와 수정할 파일

[현재 에이전트 파일 계약](../agent-files.md)에 따라 managed 에이전트의 개인 파일 원본은 회사·에이전트별 디렉터리에 있다. 실행 시 등록된 사본이 준비되고 `AGENT_HOME`과 진입 지침으로 전달된다. 기본 진입 파일은 `AGENTS.md`지만 실제 설정을 확인한다. 소문자 `agents.md`를 가정하지 않는다.

```text
<instance>/companies/<company-id>/agents/<agent-id>/instructions/
  AGENTS.md                         # 실제 설정된 진입 파일 사용
  policies/
    artifact-naming.md              # 규칙 배포 사본
```

| 파일 | 예정 변경 |
| --- | --- |
| 저장소 `doc/AGENT-ARTIFACTS.md` | 명명·위치 기록·Slack 안내 규칙의 관리 원본 추가. 기존 업로드 절차 재사용. |
| 각 에이전트의 실제 진입 파일 | 기존 내용을 보존하고 규칙 파일을 읽으라는 관리 블록만 추가. |
| 각 에이전트의 `policies/artifact-naming.md` | 동일 규칙과 규칙 버전 배포. |
| 저장소 `AGENTS.md` | 이 저장소에서 작업하는 에이전트용 참조 추가. 전사 배포의 대체로 사용하지 않음. |

`skills/paperclip/SKILL.md`는 이번 적용의 필수 수정 대상에서 제외한다. 기존 산출물 업로드·등록 절차를 그대로 사용한다. 저장소 스킬 파일 변경만으로 설치된 모든 사본이 갱신된다고 가정하지 않는다.

Instructions Editor 또는 권한 있는 기존 관리 API·도구로 원본을 수정한다. 실행 사본이나 캐시를 직접 수정하지 않는다. 보조 파일을 넣는 것만으로 자동으로 읽힌다고 보지 않는다. 현재 managed 파일은 파일 자체가 기준이며, 새 수정마다 자동 이력이 쌓인다고 가정하지 않는다.

외부 번들은 관리자가 수정할 수 있는 원본에 같은 지침을 배포한다. 읽기 전용 번들을 억지로 수정하거나 managed 모드로 자동 전환하지 않는다. 파일 참조가 불가능하면 실제로 전달되는 진입 지침에 규칙 본문을 넣고 예외를 기록한다. 전달 방법이 없으면 적용 불가로 남긴다.

### 진입 파일에 추가할 관리 블록 예시

```markdown
<!-- paperclip:artifact-naming:start -->
## 산출물 생성과 위치 안내

파일 산출물을 생성하는 작업을 시작할 때 이 진입 파일과 함께 배포된
policies/artifact-naming.md를 읽고 따른다.
managed 실행에서는 현재 AGENT_HOME 아래의 파일을 읽는다.
파일이 없거나 읽을 수 없으면 적용 완료로 간주하지 말고 문제를 보고한다.

[기본 원칙과 확인 절차]
1. 산출물은 에이전트 로컬(AGENT_HOME 등)이 아니라 프로젝트 워크스페이스 폴더에 저장하는 것을 기본으로 한다.
2. 파일 생성이 수반되는 작업은 시작 전 사용자에게 기본 프로젝트 폴더 경로를 제시하고, 해당 위치에 저장할 것인지 확인한 뒤 진행한다.
3. 작업의 기존 위치 기록을 먼저 확인하여 재시도·인계 시 같은 경로를 사용한다.
4. Slack 요청에는 원 요청 스레드로 작업명과 저장 예정 프로젝트 폴더를 확인·안내하고, 완료 시 확인된 위치와 산출물 링크를 제공한다.
5. 기존 권한·승인과 저장소별 경로 규칙을 유지한다.
<!-- paperclip:artifact-naming:end -->
```

외부 번들은 `AGENT_HOME` 대신 실제 읽기 기준을 명시한다. 동일 블록이 있으면 갱신하고 중복 추가하지 않는다. 개별 에이전트의 역할·메모·개인 지침은 보존한다.

## 2. 배포할 폴더·파일 규칙

### 작업명과 폴더

1. **프로젝트 폴더 기본 원칙:** 산출물은 에이전트의 로컬 환경(`AGENT_HOME` 등)이 아닌, 해당 프로젝트의 작업 공간(`artifacts/<company-id>/<project-name>--<project-id>/...` 또는 프로젝트 지정 폴더)에 저장하는 것을 기본으로 한다. 에이전트 개인 폴더에 산출물을 방치하지 않는다.
2. **사용자 확인(인터랙션/질문) 선행:** 파일 생성이 수반되는 작업은 실제 파일을 작성하기 전에 사용자에게 기본 프로젝트 폴더 경로를 안내하고, 해당 프로젝트 폴더에 저장할 것인지 확인(질문/동의 요청)을 거쳐 진행한다. 사용자가 별도 위치를 지정하면 그 경로를 우선한다.
3. 사용자 지정 작업명을 우선한다. 이름이 없으면 요청의 대상·행위·결과를 포함한 짧은 이름을 만든다. 예: “로그인 실패 원인을 분석하고 보고서로 정리해 줘” → `로그인 실패 원인 분석`.
4. 사용자의 언어를 유지한다. 개인정보·비밀값과 요청 원문 전체를 폴더명에 넣지 않는다. `작업`, `결과`, `final`만으로 이름 짓지 않는다.
5. 기존 이슈의 위치 기록을 먼저 읽는다. 기록이 없을 때만 승인된 실행 워크스페이스 안에서 다음 상대 경로를 정한다.

```text
artifacts/<company-id>/<project-name>--<project-id>/<issue-key>--<task-name>/
```

회사·프로젝트 ID는 실제 UUID 전체를 사용하고, `issue-key`는 `GAB-201` 같은 기존 식별자를 사용한다. 식별자가 없으면 이슈 UUID를 사용한다. 프로젝트 미연결이면 프로젝트 구성 요소 전체를 `unassigned`로 대체하며 임의 프로젝트를 생성하지 않는다. 워크스페이스·권한이 미확정이면 경로를 확정했다고 안내하지 않는다.

이름은 Unicode NFC로 정규화하고 한글·기타 문자·숫자·하이픈을 유지한다. 영문은 소문자화하며 공백과 나머지 구분자는 하이픈으로 정리한다. 경로 구분자, 제어 문자, 경로 이동 요소, 선행 점, Windows 예약 이름을 허용하지 않는다. 비거나 예약된 이름은 구성에 따라 `project`, `task`, `artifact`로 대체한다. 이름 부분은 UTF-8 60바이트 이내에서 문자 경계를 지켜 자르고 식별자는 보존한다. 실제 환경의 경로 길이·쓰기 가능 여부도 확인한다.

```text
프로젝트: 고객포털
작업: GAB-201 · 로그인 실패 원인 분석

artifacts/<회사 UUID>/고객포털--<프로젝트 UUID>/GAB-201--로그인-실패-원인-분석/
  GAB-201--로그인-실패-분석보고서--v01.md
  GAB-201--로그인-오류-재현결과--v01.json
```

UUID 표시는 예시에서만 생략했다. 폴더는 충돌 예방 수단이며 회사·프로젝트·워크스페이스 접근 권한의 대체가 아니다. 사용자 지정 위치나 저장소 규칙이 있으면 권한 범위 안에서 따르고 예외 경로와 이유를 기록한다. 에이전트 개인 폴더인 `AGENT_HOME`에 작업 산출물을 저장하지 않는다.

### 파일명과 버전

```text
<issue-key>--<deliverable-name>--vNN.<extension>
```

산출물 이름에도 같은 정규화 규칙을 적용하고 확장자는 실제 콘텐츠와 맞춘다. 최초 전달본은 `v01`, 전달 후 내용이 바뀌면 `v02` 이상을 사용한다. 기존 파일과 첨부·work product를 먼저 확인하고 게시한 결과를 덮어쓰지 않는다. 같은 업로드의 재시도는 기존 helper와 영수증을 확인하고 불필요한 새 버전을 만들지 않는다.

별도 DB 버전 예약 기능을 추가하지 않는다. 여러 생성 주체가 같은 이슈의 파일을 만들면 단일 담당자가 취합·버전 결정을 맡고 충돌 시 내용을 확인해 별도 버전으로 보존한다. 이 지침만으로 동시 쓰기나 중복 업로드가 원자적으로 차단되는 것은 아니다.

## 3. 위치 기록과 인계

경로를 정한 에이전트는 기존 이슈 문서 기능으로 `산출물 위치` 문서를 만들거나 갱신한다. 문서 키는 `artifact-location`으로 하고 기존 문서가 있으면 최신 저장 리비전을 읽어 기존 API의 동시 수정 방식을 따른다. 새 필드나 API를 만들지 않는다. 현재 문서가 기준이며, 문서 기능을 사용할 수 없는 런타임은 이슈 댓글에 같은 정보를 남기고 문서 미지원 사실을 기록한다.

기록 항목은 규칙 버전, 회사·이슈·프로젝트, 결정한 작업명, 워크스페이스 종류·ID, 상대 폴더, `예정`/`확인됨`/`사용불가`, 예외 사유다. 파일 생성·등록 후 산출물 이름과 기존 work product·첨부 링크를 추가한다. 저장 결과를 재조회하여 확인한다.

재시도·인계·재개 때는 위치 기록과 실제 파일·등록 상태를 먼저 읽는다. 제목이나 담당자가 바뀌어도 폴더를 다시 이름 짓지 않는다. 프로젝트·워크스페이스 변경으로 위치가 달라져야 하면 이전 위치·링크를 보존하고 새 위치와 변경 이유를 기록·안내한다. 기존 파일을 자동 이동하거나 삭제하지 않는다. 새 환경에서 폴더가 없으면 파일이 있다고 주장하지 않는다.

하위 작업은 자기 이슈 키로 폴더를 만들고 부모 작업에 결과를 연결한다. 파일 전달은 기존 [산출물 등록 절차](../AGENT-ARTIFACTS.md)를 사용하여 attachment·work product에 등록한다. 로컬 경로만 남겨 완료하지 않는다. 워크스페이스에 남겨야 하는 파일은 기존 `workspace_file` 참조를 사용한다.

## 4. 에이전트가 수행할 Slack 안내

기존 Slack 연결·스레드·응답/파일 전달 수단을 사용한다. 에이전트는 위치 기록과 실제 확인 결과에 근거해 안내한다. 기존 접수·상태 응답에 아래 항목을 포함할 수 있으면 함께 전달한다. 별도 Slack 봇·메시지 큐·자동 템플릿 기능은 개발하지 않는다.

### 시작 안내 및 위치 확인 예시

```text
요청을 접수했습니다.
작업: GAB-201 · 로그인 실패 원인 분석
프로젝트: 고객포털
기본 저장 예정 폴더:
artifacts/<회사 UUID>/고객포털--<프로젝트 UUID>/GAB-201--로그인-실패-원인-분석/

산출물은 위 프로젝트 폴더에 기본 저장할 예정입니다. 이 경로로 진행할까요, 아니면 다른 폴더를 지정하시겠습니까?
작업 보기: <권한이 적용되는 작업 링크>
```

작업명과 기본 프로젝트 폴더 위치를 정한 뒤, 본격적인 파일 생성 전에 기존에 허용된 응답 수단(Slack 스레드 또는 이슈 상호작용 질문)으로 사용자에게 저장 위치를 확인·질문한다. 사용자의 승인/피드백을 받은 뒤 폴더를 생성하고 작업을 진행한다. 폴더 생성 전에는 `예정`이라고 표현한다. 위치가 미확정이면 실제 이유를 알려주고 준비되면 확정 위치를 안내한다. 아직 실행하지 않았으면 진행 중이라고 주장하지 않는다.

### 완료 안내 예시

```text
GAB-201 · 로그인 실패 원인 분석을 완료했습니다.
저장 폴더: <확인한 워크스페이스 상대 경로>
산출물: GAB-201--로그인-실패-분석보고서--v01.md
열기 / 다운로드: <확인한 산출물 링크>
작업 보기: <작업 링크>
```

파일 저장·업로드·등록을 확인한 뒤 완료를 알린다. 코드 수정은 PR·커밋과 실제 경로를 전달한다. 위치가 변경되면 같은 스레드에서 변경 이유와 새 위치를 알린다. 내부 절대 경로·비밀값을 노출하지 않고 Slack 수신자의 기존 접근 범위를 지킨다.

런타임이 중간 응답을 지원하지 않으면 기존에 허용된 채널 응답 도구가 있는지 확인한다. 없으면 최종 응답에 위치와 제약을 남기고 시작 안내 미지원으로 기록한다. 두 요구사항을 모두 충족한 것으로 집계하지 않는다. 발송 실패·불명확한 결과는 기존 전달 절차로 확인하며 파일 재생성이나 무조건 재발송으로 해결하지 않는다.

## 5. 배포 순서와 적용 확인

1. **대상 조사:** 회사별 활성·휴면 에이전트, 실제 진입 파일, managed/external 구분, 파일 편집 권한, Slack 시작 응답 가능 여부를 확인한다. 파일명이나 어댑터 이름으로 수신 여부를 추정하지 않는다.
2. **규칙 원본 작성:** `doc/AGENT-ARTIFACTS.md`에 규칙·예시를 반영하고 배포 파일에 동일한 규칙 버전을 표시한다. 개인 폴더의 파일은 배포 사본이며 별도 정책 원본으로 관리하지 않는다.
3. **대표 에이전트 적용:** 기존 내용을 안전하게 백업한 뒤 진입 관리 블록과 규칙 사본을 저장한다. 백업에는 기존 접근 권한을 유지한다. 저장 직전 최신 내용을 확인하며 동시 수정 충돌 시 다시 읽어 보존한다.
4. **실제 실행 검증:** 다음 실행·안전한 재개 경계에서 규칙 읽기, 위치 기록, 파일 생성, 기존 산출물 등록과 Slack 안내를 확인한다. 실행 사본 직접 수정이나 강제 재시작은 하지 않는다.
5. **전체 배포:** 대표 검증 후 대상별로 같은 변경을 적용하고 저장 파일을 재조회한다. 아래 표를 에이전트별로 확장하여 증거를 기록한다. 실패·미지원을 따로 남긴다.
6. **신규·갱신 운영:** 기존 생성·온보딩 체크리스트에 진입 블록·규칙 사본 설치와 첫 실행 검증을 넣는다. 코드 없는 절차이므로 신규 에이전트 자동 적용을 보장하지 않는다. 규칙 개정 시 전체 배포 사본을 갱신·확인한다.

| 회사·에이전트 | 진입 파일·관리 방식 | 규칙 버전·저장 확인 | 실행·산출물 증거 | Slack 시작·완료 증거 | 상태 |
| --- | --- | --- | --- | --- | --- |
| 운영 대상 조사 전 | 미확인 | 미배포 | 미검증 | 미검증 | 계획만 작성 |

기존 폴더·파일은 일괄 이동·이름 변경하지 않는다. 진행 중 작업의 기존 위치를 먼저 기록하고 다음 산출물의 위치를 안내한다. 철회 시 배포 블록·규칙 사본만 이전 내용으로 복구하되 이후 개인 지침 변경을 보존한다. 작업 파일·이슈 위치 기록·첨부·work product는 삭제하지 않는다.

## 6. 검증과 완료 조건

| 시나리오 | 확인할 결과 |
| --- | --- |
| 작업명 지정 / 요청 본문만 지정 | 식별 가능한 작업명, 폴더와 파일명에 요청 내용 반영. |
| 한글·긴 이름·동명 작업·프로젝트 미연결 | 명명 규칙 준수, 기존 파일 보존, `unassigned` 처리. |
| 기존·신규·재개 에이전트 | 실제 진입 지침과 규칙 파일을 읽고 동일 절차 수행. |
| 인계·제목 수정 | 기존 위치 기록을 읽고 같은 경로 사용. |
| 프로젝트·워크스페이스 변경 | 이전 링크 보존, 새 위치와 변경 이유 안내. |
| Slack 요청 | 같은 스레드에 작업명·예정 폴더 안내 후 실제 결과 링크 제공. |
| 파일·업로드·발송 실패 | 확인 전 완료 주장 없음, 결과 재생성·무조건 재발송 없음. |
| 파일 누락·외부 런타임 미지원 | 누락·미지원 표시, 적용 완료로 집계하지 않음. |

배포 검증은 파일 저장·재조회와 실제 작업 실행 증거로 나눈다. 문구가 들어간 것만으로 행동 적용을 입증하지 않는다. Slack 실검증은 권한이 있는 테스트 스레드에서 수행하고 메시지·파일·work product 링크를 남긴다. 모의 응답만으로 실제 안내 완료를 주장하지 않는다.

지침 기반 방식은 에이전트의 누락·해석 차이, 동시 파일 쓰기, 중간 응답 미지원까지 시스템에서 강제하지 못한다. 이를 대상별 검증 상태로 관리한다. upstream 충돌 가능성은 수정한 저장소 문서에 남지만 제품 코드·DB·실행 계약의 충돌 범위는 추가하지 않는다.

계획·지침 문서 변경에는 diff 검토와 공백 검사를 수행한다. 타입 검사·빌드·제품 회귀 테스트는 필요하지 않다. 실제 배포 시에는 위 행동 시나리오를 검증한다.
