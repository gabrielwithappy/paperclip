# OpenCode MCP 도구 이름 길이 오류 수정 계획

## Outcome and scope

하루 에이전트가 `stopped before completing this turn`으로 종료되는 원인을 수정하기 위한 계획이다. 계획 QA 이후 사용자가 코드 수정·커밋·푸시·서버 재시작을 승인했다. 이 문서는 구현과 운영 반영 증거를 이어서 기록한다.

기존 [외부 어댑터 계획](2026-11-14-opencode-mcp-external-adapter.md)의 후속 결함으로 다룬다. 목표는 현재 사용 중인 128자 제한 모델에서 Paperclip이 전달하는 MCP 도구를 실제 호출하고 답변까지 완료하는 것이다. 다른 모델의 더 짧은 제한까지 지원한다고 일반화하지 않는다.

## Decisions and evidence

### 확인된 원인과 검증 공백

- 운영 실행 로그의 실제 오류는 `Function name at index 6 exceeds 128 character limit, got 137 characters`이다. 일반적인 채팅 종료 문구만으로 OAuth 문제라고 판단하면 안 된다.
- `server/src/services/mcp-tool-names.ts`는 Claude의 `mcp__paperclip-assigned__` 접두사를 고려하여 게이트웨이 이름을 최대 103자로 제한하고, 원래 도구로의 매핑을 보존한다.
- `extensions/opencode-mcp-adapter/src/mcp.ts`는 서버 키를 `paperclip_run_` + SHA-256 앞 24자리, 총 38자로 생성한다. 설치된 OpenCode 1.18.9에서 모델에 전달하는 이름은 서버 키 + `_` + 도구 이름이다.
- 이번 98자 도구는 `38 + 1 + 98 = 137`자가 됐다. 기존 게이트웨이 최대 길이를 적용하면 `38 + 1 + 103 = 142`자까지 가능하다.
- 실제 OpenCode와 기본 어댑터, 로컬 MCP·모델 fixture로 같은 137자 오류를 재현했다. 모델 fixture는 128자를 초과하면 HTTP 400을 반환했고, 실패 전 도구 호출은 0회였다. 이는 실패 재현 성공이며 수정 성공 증거가 아니다.
- 앞선 테스트는 `read_fixture`처럼 짧은 이름을 사용했다. MCP 연결, 인증, 짧은 도구 호출, 설치 후 진단 성공은 긴 이름의 모델 호환성을 보장하지 않았다.

재현 보조 파일은 `/tmp/paperclip-opencode-name-limit-verification.test.mjs`에 있으며 일시적 진단 자료다. 구현 시 지속 가능한 회귀 검증을 플러그인 테스트에 편입한다. 이 계획에는 실제 토큰, 회사 식별자, Slack 링크를 저장하지 않는다.

### 소유권과 수정 방식

수정 소유자는 외부 OpenCode 어댑터다. Paperclip의 `runtimeMcp.getServers()` 계약과 게이트웨이의 정책·이름 매핑을 재사용한다. 인증, 회사 격리, 승인, 감사, tools/call 매핑은 기존 서버가 소유한다. 공통 heartbeat·DB·UI 계약 변경은 현재 필요하지 않다.

서버 키 예산은 `128 - 1 - 103 = 24`자 이하다. 선택안은 `pc_mcp_` + SHA-256 앞 16자리(23자)다. 이 경우 최대 모델 도구 이름은 127자다. 원래 서버 표시 이름 대신 connectionId 기반의 결정적 키를 사용하여 같은 표시 이름의 연결도 구분한다.

해시 길이만 믿고 충돌이 없다고 가정하지 않는다. 생성한 키의 중복을 자격증명 파일 생성 전에 검사하고 충돌 시 명확하게 실패시킨다. 새 예약 영역은 `^pc_mcp_[a-f0-9]{16}$` 패턴과 실제 생성 키로 한정하고, 기존 `paperclip_run_` 예약 영역의 충돌 거부도 유지한다. 사용자의 무관한 `pc_local`, `pc_mcp_custom` 같은 MCP는 보존한다. 기존 파일을 자동 삭제하거나 다른 서버 설정을 덮어쓰지 않는다.

게이트웨이 도구 이름을 어댑터에서 자르거나 바꾸지 않는다. 모델에 보이는 이름과 OpenCode의 tools/call 역매핑이 정상 동작하는지 실제 CLI로 확인한다. 서버 키 변경으로 충분하지 않은 입력이 발견되면 완료 주장을 멈추고 해당 경계를 계획에 추가한다.

## Approach

1. **운영 코드와 개발 작업을 분리하고 재현을 회귀 검증으로 편입한다.** 현재 운영 설치 경로와 분리된 checkout에서 개발·빌드·테스트한다. 현재 98자 사례와 게이트웨이 상한 103자 사례를 실제 OpenCode 1.18.9 + 기본 executor + 로컬 모델 fixture로 실행한다. 모델 fixture는 수신한 모든 function name을 검증하고 128자 초과를 거절한다. 변경 전 137/142자 실패 및 호출 0회, 변경 후 정상 호출·응답을 비교한다.
2. **어댑터의 이름 생성과 충돌 검사만 수정한다.** `src/mcp.ts`에 짧은 키 예산과 결정적 생성, 중복 검사, 신·구 예약 영역 처리를 둔다. 같은 표시 이름/서로 다른 connectionId, 병렬 실행, 순서 변경의 결과를 검증한다. 게이트웨이·connections control·projects 등 runtime MCP 진입점의 이름 길이를 조사하여 103자 상한의 적용 범위를 명시한다.
3. **버전과 세션 전환을 일치시킨다.** 패키지와 `DELIVERY_VERSION`을 0.1.1로 함께 올린다. 기존 mcpIdentity의 버전 반영을 재사용하여 0.1.0 세션을 새 도구 집합으로 갱신한다. 세션 기록은 삭제하지 않는다. 토큰 교체만으로는 불필요한 세션 초기화를 하지 않는 기존 동작도 유지한다.
4. **기존 fixture·문서의 전제를 갱신한다.** `test/execute.test.mjs`의 이전 접두사 탐색 등 결합된 fixture를 수정하고 README의 예약 영역·제한을 갱신한다. 필요한 경우 어댑터 기능 map만 갱신한다. 별도의 MCP 프록시나 코어 이름 제한 유틸리티를 중복 구현하지 않는다.
5. **로컬 검증과 QA를 수행한다.** 아래 인수 조건과 기존 자격증명·세션·거부 경로 검증을 실행하고 QA가 결과를 검토한다. 실제 운영 디렉터리에 연결된 dist를 서비스 실행 중 덮어쓰지 않도록 별도 위치에서 빌드·검증한다.
6. **승인된 구현 작업에서 운영 반영과 실제 작업 회복을 수행한다.** 실행 중/대기 중 작업과 ingress를 확인하고 `scripts/local-service/README.md`의 drain·ingress 차단·모든 writer 정지·새 백업 절차를 따른 뒤 운영 checkout을 변경한다. 검증된 빌드를 설치·활성화하고 서버를 재시작한다. 등록 목록뿐 아니라 실제 로드된 0.1.1 진단 마커를 확인한 뒤 제한된 인수 작업을 수행한다. 성공 후 저장한 ingress·자동화 설정을 복원한다. 활성 실행을 강제 종료하거나 임의 DB 수정으로 상태를 바꾸지 않는다.
7. **실제 사용자 경로를 확인한다.** 먼저 실제 사용 모델로 제한된 읽기 전용 에이전트 작업을 실행하여 MCP 도구가 포함된 요청·도구 호출·최종 답변을 확인한다. 이후 실패 작업의 최신 상태와 부작용 여부를 재확인하고 정상 API를 통해 필요한 작업만 재개한다. Slack 유입 건은 최종 응답이 해당 채널에 게시되는 것까지 검증한다. 이전 실패 기록은 성공 재시도로 지우거나 누락하지 않는다.

우선 플러그인 디렉터리에서 `pnpm typecheck`, `pnpm build`, `pnpm test`를 실행한다. 현재 test 스크립트는 실제 CLI fixture까지 포함한다. 코어 이름 계약을 참조한 검증도 확인한다. map 수정 시 `node scripts/check-maps.mjs`를 실행한다.

PR-ready 완료 주장 전 저장소 지침에 따라 `pnpm -r typecheck`, `pnpm test:run`, `pnpm build`를 실행한다. 독립 패키지인 extensions 검증은 이 루트 명령으로 대체되지 않는다. 실행 불가 또는 기존 실패는 원인·범위와 함께 별도로 남긴다. UI·브라우저 suite는 이번 변경이 해당 경로를 건드리지 않는 한 추가하지 않는다.

## 운영 위험과 복구

- 동일 adapter type의 외부 override는 모든 OpenCode 에이전트에 영향을 준다. 재시작 전 실제 실행·큐 상태를 다시 확인한다.
- 로컬 경로 설치와 모듈 캐시 때문에 등록 파일의 버전만 바뀌어도 새 코드가 로드됐다고 단정할 수 없다. 재시작 이후 실제 진단 마커 및 도구 실행으로 증명한다.
- 반영 전 현재 등록·설정과 빌드 산출물을 보관하고 기존 서비스 백업 절차를 따른다. 새 회귀가 발생하면 ingress를 막고 drain 후 이전 빌드·등록을 복원하여 서비스를 확인한다. 이전 0.1.0으로의 복귀는 이번 긴 이름 오류를 해결하지 못하므로 영향 작업은 차단 상태로 명시한다.
- 사용자 MCP의 도구나 향후 103자를 넘는 별도 서버 도구까지 모두 지원한다고 주장하지 않는다. 확인된 runtime 입력과 현재 모델의 128자 제한을 인수 범위로 기록한다. 더 짧은 모델 제한·모델 교체·OAuth 재인증은 별도 문제다.

## QA review

독립 QA 에이전트 `qa_opencode_name_budget`가 관련 코드와 계획을 읽기 전용으로 검토했다. 초회 MEDIUM 2건을 반영하고 재검토 PASS를 받았다.

1. **사용자 MCP와의 과도한 예약 충돌:** `pc_` 전체 예약을 폐기하고 전용 23자 키·정확한 예약 패턴·무관한 `pc_*` 설정 보존 검증으로 수정했다.
2. **운영 checkout 수정 경계:** 개발·전체 검증을 격리 checkout에서 수행하고, 운영 경로 변경 전 drain·ingress 차단·writer 정지·백업을 명시했다.

재검토 결과 남은 중대한 지적은 없다. 이 결과는 계획의 적절성에 관한 것이며 구현 성공이나 운영 복구를 의미하지 않는다. 계획 리뷰 시점에는 테스트·운영 호출을 실행하지 않았다.

### 구현 QA 및 검증

- 같은 QA 에이전트가 격리 checkout의 실제 변경을 검토하여 PASS를 보고했다. 보안·정확성·회귀 검증의 중대한 발견은 없다.
- 변경 전 98/103자 도구가 실제 CLI 모델 요청에서 각각 137/142자로 거절됐다. 짧은 도구의 red 실패는 새 키 길이 assertion으로 인한 것이며 provider 거부가 아니다.
- 수정 후 독립 플러그인 typecheck·build 성공, 실제 CLI 포함 17개 테스트 전부 통과. 긴 도구는 122/127자이며 정확한 원래 이름 호출과 최종 응답·토큰 교체·제거를 검증했다.
- 전체 `pnpm build` 성공. 전체 타입 검사는 server tsc가 커널 OOM으로 두 차례 종료(137)되어, 테스트를 중지한 뒤 서버 타입 검사를 단독 재실행하여 성공했다. 재귀 타입 검사 명령 자체의 종료 상태는 137이며 이를 전체 성공으로 바꾸어 기록하지 않는다. 전체 `pnpm test:run`은 채팅 shard 실행 중 자원 경합을 해소하려고 중지했으며 전체 통과로 간주하지 않는다.
- 코어 이름 계약 테스트 2개 통과. 게이트웨이 names는 boundedMcpToolName을 경유한다. 연결 제어 도구는 connections_search/connection_request, 프로젝트 도구는 create_project/list_project_repositories/list_projects/create_task/set_task_title로 현재 103자 이하다.

### 운영 반영 결과

- 소스 변경은 `90a80845e2`로 커밋하여 `fork/devel`에 푸시했다. 배포된 plugin bundle은 QA에서 테스트한 격리 bundle과 동일하다.
