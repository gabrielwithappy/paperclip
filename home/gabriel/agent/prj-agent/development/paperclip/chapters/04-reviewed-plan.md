# 4장. 리뷰한 구현 계획과 검증 기준

## 계획의 현재 상태

검토한 계획은 외부 어댑터 방식의 타당성 확인을 시작하기에 적합하다는 독립 리뷰를 받았다.
이는 구현 완료나 실행 성공 판정이 아니다. 계획 원본은 저장소의
`doc/plans/2026-11-14-opencode-mcp-external-adapter.md`다.
이 장은 원본 계획의 설명이며, 이후 구현 상태는 원본과 코드에서 확인한다.

## 첫 단계는 얇은 래퍼의 타당성 확인

기존 OpenCode execute 함수에는 별도의 MCP launch-env를 받는 공개 훅이 없다.
외부 패키지가 기존 함수를 호출하는 것만으로 문제가 해결된다고 가정하면 안 된다.
현재 후보는 private 인증 파일과 비밀이 없는 설정 참조를 만들고 base execute를 재사용하는 래퍼다.

OpenCode 1.18.9가 MCP 헤더에서 파일 참조를 지원하고 inline 설정과 세션 재개에서도 올바르게 처리하는지
가짜 인증값으로 먼저 증명해야 한다. 파일 참조 문법은 검증 전 설계 후보이며 사용 예제로 확정하지 않는다.
실제 토큰은 영구 agent 설정, 프롬프트, argv, 로그, sessionParams에 넣지 않는다.

이 후보가 성립하지 않으면 독립 실행 구현과 작은 공개 실행 훅 추가를 비교한다.
본체 수정 없는 방식이 불가능한 결과가 나오면 계획과 변경 규모를 다시 결정해야 한다.
비밀을 전역 process.env에 넣거나 영구 설정에 쓰는 우회는 허용하지 않는다.

## 구현 책임과 수명

서버는 회사·에이전트·작업 권한과 OAuth를 소유한다. 어댑터는 전달된 게이트웨이 정보를 CLI 형식으로 변환한다.
private 디렉터리와 파일은 실행마다 분리하고 최소 권한으로 만들며, 프로세스 종료 후 정리한다.
사용자 MCP와 provider 설정은 보존하고, 이름 충돌과 잘못된 설정은 명확하게 보고한다.

제한된 로컬 sandbox와 원격에서는 호스트 임시 파일이 읽힌다고 가정하지 않는다.
기존 파일 전달과 허용 경로로 지원을 증명하거나, 미지원 실행 모드를 시작 전에 거부한다.
로컬 구현이 동작했다고 해서 인스턴스의 모든 원격 에이전트에 적용하지 않는다.

## 리뷰에서 보완한 세 가지

1. 설치 레코드와 실제 활성 구현을 구분한다. cold restart와 import 실패 주입을 포함한다.
2. supportsToolRefreshOnResume를 명시적으로 다룬다. 기존 세션 갱신과 새 세션 전환을 나눠 검증한다.
3. Ask first 승인 후 중복 실행을 검증한다. 서버가 승인된 호출을 한 번 실행하면 재개한 에이전트는 저장된 결과를 사용한다.

## 인수 증거

가짜 MCP 서버를 사용해 이전 어댑터의 호출 누락과 새 경로의 호출 성공을 관측한다.
기존 회사 경계, Off·Ask first, 권한 회수, 동시 실행, 토큰 교체, 취소·실패 정리를 검증한다.
Ask first는 작업에 연결된 실제 승인 경로에서 실행 횟수 1회와 재개 후 추가 실행 0회를 확인한다.
거절과 취소가 새 외부 호출을 만들지 않는지도 확인한다.

마지막에는 격리 Paperclip 인스턴스에서 발급부터 OpenCode와 게이트웨이를 거쳐 실제 도구 호출까지 검증한다.
fixture 성공, 서버 Test 성공, 실제 Todoist/OpenCode 성공을 서로 다른 증거로 보고한다.
운영 설치·활성화는 영향 대상과 rollback이 검토 가능한 뒤 별도로 진행한다.
