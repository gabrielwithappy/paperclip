# 2장. Todoist 재인증 안내의 실제 원인

## 초기 응답과 추가 관측

이번 조사에서는 Todoist 인증을 마친 뒤에도 에이전트가 로그인을 반복 요청했다.
처음에는 권한 변경 이전의 검색 결과를 재사용한 후속 응답이 확인됐다. 그 응답들에서는 새로운 연결 조회가 없었다.
하지만 이를 유일한 원인으로 보면 안 됐다. 새로 조회한 실행에서도 다른 실패가 이어졌기 때문이다.

추가 실행은 기존 연결의 ready 상태를 확인했다. 이어 실제 Todoist 도구를 찾지 못해 연결 설정용 MCP 경로를
살폈고, 도구 목록에는 connections_search와 connection_request만 나타났다.
그 뒤 공급자 주소인 https://ai.todoist.net/mcp 를 인증 없이 직접 호출했다. 401 응답을 받은 에이전트는
기존 Paperclip 인증이 미완료라고 판단하고 추가 연결 초안을 만들었다.

## 401의 의미를 호출 경로와 함께 읽기

공급자 MCP 서버에 무인증 요청을 보내 받은 401은 그 요청에 인증이 없었다는 증거다.
Paperclip 서버에 저장된 OAuth 인증이 만료됐다는 증거로 사용할 수 없다.
Paperclip의 인증된 게이트웨이 경로를 통해 같은 서비스의 get-overview를 호출했을 때는 정상 성공했다.

따라서 이 사건에서 확인된 문제는 두 단계다. 이전 판단을 검증하지 않은 응답 반복이 있었고,
새 조회 이후에도 어댑터가 실제 MCP 도구를 등록하지 못하는 문제가 있었다.
서버 테스트 성공을 전체 에이전트 경로의 성공으로 보고했던 초기 설명도 이 구분에 맞게 수정해야 한다.

## 코드에서 확인한 전달 누락

서버의 heartbeat 실행 경로는 runtimeMcp를 어댑터에 전달한다. 조사 시점의 OpenCode 어댑터는
runtimeTools 환경변수를 만들지만 runtimeMcp.getServers()를 OpenCode MCP 설정에 적용하지 않는다.
Codex와 Claude에는 이 목록을 소비하는 코드가 있다.

OpenCode 자체는 MCP를 지원한다. 이번 누락은 Paperclip과 OpenCode를 잇는 어댑터에서 발생했다.
CLI에 Todoist를 별도로 등록해 재인증하는 방법은 Paperclip의 회사 권한과 승인 경로를 우회할 수 있으므로
기본 복구 방법으로 삼지 않는다.

## 일반화할 진단 원칙

1. 현재 연결을 새로 조회하고 저장·인증·권한·실제 호출 상태를 나눠 기록한다.
2. 오류가 발생한 URL과 인증 주체를 확인한다. 공급자 직접 호출과 Paperclip 게이트웨이를 구분한다.
3. 도구 목록을 확인한다. 연결 설정 도구만 있는지 실제 앱 작업 도구도 있는지 살핀다.
4. 서버 테스트와 실제 에이전트 실행을 각각 검증한다.
5. 최신 증거가 과거 판단과 다르면 요약과 후속 응답을 갱신한다.
